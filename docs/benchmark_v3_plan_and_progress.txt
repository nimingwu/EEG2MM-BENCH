EEG2X-Benchmark v3 长期计划与当前进度

本文是 v3 重构的活文档，随进度更新。记录三件事：长期要走到哪里、现在已经做到哪里、下一步按什么顺序做。代码的详细结构说明见 jieshao_benchmark_v3.txt，本文不重复。

一、总目标与不可动摇的约束

v3 的目标是把 v2 在推进中长出来的重复结构推倒重写，同时保持实验逻辑与 v2 一致。具体有五条。

第一，框架只写一遍，编码器可插拔。统一框架的不变量是只换 EEG 编码器，目前有 atm_s、labram、reve、luna、enigma 五个。基线相反，编码器固定，命令行给基线传编码器必须直接报错，而不是悄悄忽略。

第二，编码器只写一遍，跨任务共享。之后接入视频与文本任务时，labram、luna、reve 也要复用同一份实现，所以编码器层从一开始就独立于任务存在，协议里预留了 forward_tokens。

第三，只有一个入口。根目录只有 benchmark.py，下设 run、preprocess、verify、list 四个子命令，被试默认取全部。

第四，预处理一个数据集一个文件，文件内按 profile 分支，不再有根目录下的一堆 preprocess 脚本，eeg2image_benchmark_loader.py 降级成辅助库 common.py。

第五，刺激侧提升为一等概念，图像如何变成回归目标放在 eeg2x/targets/ 下，不再藏在模型目录里。

另有几条硬约束，任何时候都不能违反。全局种子固定为 2000，运行时必须设置 PYTHONHASHSEED=2000。所有预处理与运行产物必须落在 benchmark 仓库内，这是可追溯性要求。完整 ATM、AVDE、ENIGMA 是基线，不能换编码器。LUNA 使用与其余编码器不同的优化器配方，这是有意的偏离，代价与依据记录在 v2 的 LUNA_TRAINING_DEVIATION.md，v3 用 EncoderSpec.optimizer 把它数据化，但结论不变，LUNA 的行不能与其他编码器并列排名。另外，v3 仓库里不允许留任何临时性的模型健康监控代码，这类东西只属于诊断过程，不属于 benchmark。tab_benchmark_setup.tex 与 tab_benchmark_setup_en.tex 两个表格文件暂时冻结，不要改动。

二、长期路线

第一阶段是 EEG 到图像重建，也就是当前阶段。目标是让 v3 完全承接 v2 的图像重建实验，包括框架的五个编码器、三个基线、噪声对照实验、完整的训练链路和单元测试。这一阶段完成的标志是：五个编码器与两个基线的推理结果与 v2 在容差内一致，噪声对照可以一键复现，训练阶段不再是桩，测试覆盖编码器契约、checkpoint 兼容、路径适配、预处理分派、指标语义与命令行守卫。

第二阶段是 EEG 到视频。复用同一套编码器与同一套框架阶段表，新增视频刺激侧的目标提取与视频指标，任务接口新增 video 分支。

第三阶段是 EEG 到文本。同样复用编码器与框架，新增文本刺激侧与文本指标，文本任务接口已经在 eeg2x/tasks/text.py 预留。

检索任务与分类任务暂不考虑，接口留在 eeg2x/tasks/image.py 里但不接线。最终形态是 v3 成为唯一在用的 benchmark，v2 转为历史参照与结果存档。

四、本次会话做完但一次都没有跑过的部分：噪声对照接线

噪声对照回答的问题是模型到底有没有在用 EEG：把整段测试集 EEG 换成标准正态噪声，权重全部冻结，图像目标与超参一律不动，照常推理与评测。共享实现在 eeg2x/noise_control.py，早期迁移时已经把实现搬全了，缺的只是接到注入点上。

框架侧改了三个文件。eeg2x/frameworks/only_clip/embed.py 增加 noise 与 noise_seed 参数，在取每个 batch 前注入噪声，并从编码器读取 valid_samples，使 LUNA 尾部二十四个结构性零填充不被替换，否则会触发它 forward 里的零填充断言。噪声条件与种子写进 embedding 的 HDF5 属性与 manifest。eeg2x/frameworks/only_clip/pipeline.py 把输出根改为干净输出目录下的 noise_control 子目录，结构上不可能覆盖干净结果；收尾时写旁挂的 noise_meta.json，并调用 validate_noise_outputs 对比干净与噪声两套图，确认注入真的生效而不是开关接错了地方。eeg2x/cli.py 给 run 与 verify 都加了 --noise 与 --noise-seed，verify 在噪声条件下自动改比 v2 的噪声参照。

基线侧改了三个文件。eeg2x/baselines/enigma/runner.py 与 eeg2x/baselines/avde/runner.py 把噪声参数透传下去。ENIGMA 与 AVDE 的 pipeline 本身在早期移植时就带着完整的噪声实现，只是上层没有入口。eeg2x/baselines/avde/pipeline.py 的 run_avde 新增噪声参数，checkpoint 仍从干净根目录读，生成、评测与 run_config 改写进 noise_control 子目录。

验证状态必须说清楚：只对 eeg2x/cli.py、only_clip/embed.py、only_clip/pipeline.py 做过语法解析，三个文件通过。基线那三个文件的语法检查没有跑成，当时 shell 停在 v2 目录，python 解释器路径不存在，命令直接失败。所以基线三个文件连语法都还没验过，数值对照更是一次都没做。

完整 ATM 的噪声注入点在 v2 里与框架共用同一个函数，理论上在 v3 会随框架的 embed_split 一起白拿，但 v3 的完整 ATM 还没有只推理入口，所以这部分暂时谈不上接线。

七、环境设计：一套代码，多套环境

原来的 requirements-v3.txt 假设整个 benchmark 能在一个 Python 环境里跑，这个假设是错的。图像框架依赖 diffusers 0.30 与 SDXL，视频框架依赖 AnimateDiff 与另一套 diffusers，LaBraM 依赖 braindecode 1.3.2，LUNA 依赖 rotary_embedding_torch，eegvid_nice 依赖 torch_geometric，把这些版本锁进一个环境只会互相牵制。所以 v3 改为多环境设计。

仓库不再维护唯一的 requirements-v3.txt，而是在 environments/ 下按用途给出若干份固定版本的说明，例如 image.txt、image-braindecode.txt、image-luna.txt、video.txt、text.txt、retrieval.txt。每一份对应一组固定依赖；图像的三份对应同一个 Python 3.11 环境，仓库本身不负责创建环境。根 README.md 与 environments/README.md 已经写明每种环境的创建步骤：按用途建 venv、安装对应 requirements、再用该环境的解释器运行 benchmark.py；检索环境另写了 NeuroAI 四个包的安装方法、EEG2X_EEGBENCH_ROOT 与 EEG2X_EEGBENCH_PYTHON 的用法。

v2 的统一框架在四个数据集上实际上是用同一个 eeg2x-atm 环境跑完 atm、labram、reve、luna 的，ENIGMA 也在其中；AVDE 使用独立的 /datas/linshishangchuan/avde。历史图像环境已经复制到 /datas/linshishangchuan/11-3-image-env/eeg2x-atm，包含 braindecode 1.3.2 与 rotary 0.8.9，复制时漏掉的 pandas.util.version 已从基础环境补回。因此 v3.1 的安装说明以一个 image 环境装三份 requirements 为主，拆成三份只是说明额外依赖。

运行时把环境当成参数而不是仓库属性。每个编码器已经在 EncoderSpec.required_packages 里声明依赖，基线也会声明自己的依赖；CLI 在构造模型前检查当前解释器，缺包时直接报错，并指出应该换用哪一份环境说明。benchmark.py env 子命令打印当前解释器、各包的版本，以及在这个环境下能跑哪些模型、编码器与数据集。

环境之间只通过产物交接：HDF5、checkpoint、评测报告，不共享运行时对象，也不要求同一个解释器能导入所有模块。因此导入路径必须保持惰性：LaBraM 的 braindecode 在构造函数里导入，LUNA 的实现只在构造时导入，torch_geometric 只在 eegvid_nice 分支导入。

环境本身不放在仓库里，也不写死路径。当前用哪个解释器由使用者提供；已知可用的解释器与恢复步骤都写在 environments/README.md，不依赖某台机器上的旧路径。权重缓存位于 /datas/hf-cache。

环境恢复后的验证顺序建议如下。第一步，对本次改过的文件做导入与语法检查。第二步，跑框架的噪声对照，先跑 atm_s 的 ThingsEEG sub-01，因为 v2 在 artifacts/only_clip_linear_seed2000/atm/sub-01/noise_control/evaluation/generation_clip.json 有现成参照，可以直接用 verify 的噪声模式对比。第三步，跑 luna 的噪声对照，验证 valid_samples 分支确实只替换前 256 个采样。第四步，跑 enigma 与 avde 的噪声对照，两个基线在 ThingsEEG sub-08 上都有 v2 的噪声参照。

九、视频重建的合并范围（已确认）

视频重建代码在 /datas/eeg_benchmark_project/fuxian/fuxian-eeg2video-1/EEG2X-Benchmark-v2，最终产物清单见同目录的产物路径.txt，实验数值以实验报告10.txt 为准，tab_raw_data.tex 暂不改动。纳入 v3 的范围是：三套数据集（SEED-DV 二十名被试、Smit2025 二十名、EMD 六名）各五个统一框架编码器（eegnet、labram、reve、luna、eegvid_nice），合计 228 条轨道；外加两族 Orig 基线，即 EEGVid Orig 与 EEG2Video Orig。MindCine 不纳入。

Orig 实际可用的轨道是五条。EEGVid Orig 在三个数据集上各一条，EMD 只保留 sub-02_k1250。EEG2Video Orig 只有 Smit2025 的 sub-01 与 EMD 的 sub-01 有报告；SEED-DV 的 EEG2Video Orig 没有产物，只有 shared 目录，暂不纳入。

合并的主要难点：视频仓库自带一份 vendored 的 LaBraM、REVE、LUNA，与 v3 基于 braindecode 的 LaBraM 不是同一份实现，需要先做权重与输出等价性验证；视频是 Scheme D 加 AnimateDiff 的另一套框架，不是 Only-CLIP；目标空间是 CLIP 文本嵌入而非图像嵌入；噪声语义是匹配均值方差的零均值高斯，与图像的标准正态不同；产物在 runs 下而非 artifacts 下；模型根目录靠环境变量在 import 时读取。

已经迁入 v3 的部分：eeg2x/tasks/video.py 提供 VideoSample 与输出契约；eeg2x/metrics/video_generation.py 提供七项指标及 shuffled 与 delta 版本，并已注册；evaluation/registry.py 增加 video_generation 条目，evaluator.py 增加 gt_frames 真值提取与视频预测解析；datasets.py 增加三套视频数据集与每个数据集乘编码器的 profile 映射，DatasetSpec 增加 task 字段；profiles_video.py 整体迁入视频 profile，profiles.py 只合并 task_id 为 video_generation 的条目；preprocessing 下的视频 loader 拆成 seed_dv、ds005662、eeg_video_action、ds008257 四个模块，共享 video_common，preprocessing/__init__.py 增加视频分派；frameworks/eeg2video/ 迁入 Scheme D 加 AnimateDiff 框架与 vendored 编码器，pipeline.py 实现 generate 与 evaluate 两阶段并支持噪声条件；baselines/eeg2video_orig/ 与 baselines/eegvid_orig/ 是两条 Orig 链的只推理适配器，checkpoint 与共享缓存用软链接接入，不复制；CLI 增加 eeg2video 框架、视频数据集、两条 Orig 基线与 --generator-dtype。

已经验证：SEED-DV 的 eegnet sub-01 在 v3 中重跑了 200 条片段，七项指标与视频仓库的 report.fp16.json 逐位相同，最大差为 0；两条 Orig 基线的 load() 预检都通过，checkpoint 与共享缓存能通过软链接找到；SEED-DV 的预处理已在 v3 中跑通，train 与 test 两个 HDF5 的 data、gt_frames、event_concept、stimulus_id、caption、channel_names 与视频仓库的产物逐元素相等，字节哈希不同只来自 HDF5 变长字符串的存储元数据。移植中发现并修复了一个缺口：v3 的 write_common_h5_metadata 少了 seed_protocol、seed_value、seed_state_json、seed_fingerprint 四个属性，补上后 v3 产物才能通过 validate_protocol_v2。另一个差异是 encoder_window_specs_json：视频仓库的旧 H5 写在 eegvid_nice 加入之前，所以只有四个编码器，v3 的当前代码写五个，这是版本差而不是数据差。

噪声条件也已在 SEED-DV 的 eegnet sub-01 前两条片段上跑通：产物落在 noise_control/，与干净帧不同（平均绝对差 31.6/255），旁挂 meta 已写。视频噪声是匹配每个试次自身均值与方差的零均值高斯，与图像侧的标准正态不同，这一点在合并时保留为两套语义。

视频训练阶段已经验证。用 /datas/linshishangchuan/eeg2video 环境，在 SEED-DV sub-01 上对 labram、reve、luna 各跑完整的 Scheme D 两阶段训练（stage one 200 epoch，stage two 150 epoch）。三个编码器的逐 epoch MSE 与视频仓库的历史记录最大差为 0，最终 stage_one.pt 与 stage_two_linear.pt 的所有张量与 v2 逐位相等；checkpoint 的 encoder 元数据、窗口几何与 model_input_normalization 也与 v2 一致。

训练已经接入 CLI：benchmark.py run --dataset seed_dv --model eeg2video --encoder labram --subjects sub-01 --stages train。视频阶段 epoch 用 --video-stage-one-epochs 与 --video-stage-two-epochs，batch 用 --video-batch-size；--stages train generate evaluate 可以在训练后直接继续生成与评测。训练由 eeg2x.frameworks.eeg2video.train_entry 在独立子进程里执行，checkpoint 写到 artifacts/<dataset>/eeg2video/<subject>/<encoder>/checkpoints，推理优先使用这份 v3 checkpoint，缺失时才回落到视频仓库的干净轨道。

尚未完成：EEGVid Orig 与 EEG2Video Orig 的生成实测（只做了 load 预检）、vendored 编码器与 eeg2x.encoders 的去重验证、视频训练在更多被试与更多数据集上的批量验证。

编码器去重是当前最大的未决问题。视频框架沿用视频仓库 vendored 的 LaBraM、REVE、LUNA，因为视频 checkpoint 是按它们的参数布局与池化方式训练的：vendored LUNA 对 query 维取均值，而 v3 图像侧的 LunaEncoder 用了一个带参数的注意力池 LunaTemporalPool；vendored LaBraM 是作者实现，v3 图像侧是 braindecode 1.3.2 的实现。直接换成 v3 的编码器会导致 state_dict 不匹配。要真正做成「编码器只写一遍」，需要二选一：把一侧的 checkpoint 做键映射与池化等价转换，或者重训一侧；在此之前，视频部分与图像部分各自保留一份 labram/reve/luna。eegnet 与 eegvid_nice 是视频专有的，不存在重复。

十、文本生成的合并（进行中）

文本代码在 /datas/eeg_benchmark_project/fuxian/fuxian-GLIM/EEG2X-Benchmark-v2-GS，最终产物清单见同目录的产物路径_eeg2text.txt，环境是 /datas/linshishangchuan/glim_2。四套数据集是 ZuCo1、ZuCo2、TMNRED、Chisco；本轮先用 ZuCo2 与 Chisco 验证推理。

已经迁入 v3 的部分：metrics/semkey_metrics.py 与 tokenization.py 提供 15 项 SemKey 指标并已注册；evaluation 的文字分支读取 target_texts_json 并把 mtv_references 传给 MTV BLEU；sentence_generation 的默认指标改为 SemKey 套件；frameworks/glim/ 迁入 GLIM 核心（glim_v2）、文本基类与 datamodule、LaBraM 与 LUNA/REVE 适配器、third_party；pipeline.py 按 checkpoint 的 hyper_parameters 选择 LM 与 prompt 条件，生成句子并评测；datasets.py 增加 zuco2 与 chisco；CLI 增加 glim 框架、文本编码器与 glim_orig 基线。

已经验证：在 ZuCo2 的 YAC 被试上，v3 生成的 44 句与原始 generate_sentence_predictions.py 在当前环境下的输出逐字相同（44/44）；GLIM 主模型的 checkpoint 在 v3 里加载为 missing=0、unexpected=0。评测层方面，用 v3 重算已有的 zuco2_glim 预测，BLEU 四项与 SBERT cosine 与原始 report_semkey.json 完全一致，Frechet 差 5e-9，四项 n-way 差在 1.5e-4 以内（随机试验与跨机器 RNG 漂移），5 项依赖 NLTK 的指标因为环境缺少 punkt_tab 与 stopwords 语料返回 nan。

完整验证结果：ZuCo2 的 glim 变体跑完 1093 条，Chisco 的 glim 跑完 3000 条，ZuCo2 的 GLIM Orig 跑完 1093 条，样本数都与参考一致。指标与参考的差异在小数点后第二到第三位，来源有两个：当前环境重新生成的句子与存档预测不同（YAC 上与原始脚本逐字一致 44/44，但存档预测是另一台机器生成的，只有 17/44 相同），以及 n-way 的随机试验。评测层用存档预测重算时 BLEU 四项与 SBERT 完全一致，说明差异来自生成而非评测。

阻塞：5 项依赖 NLTK 的指标（content recall、dist-1/2、head entropy、length MAE）因为环境缺少 punkt_tab 与 stopwords 语料而返回 nan；下载语料不是安装新的 Python 包，但需要使用者确认是否允许。其余 10 项已能计算。

文本训练已经接入 CLI：benchmark.py run --dataset zuco2 --model glim --encoder labram --stages train inference。训练从源 checkpoint 的 hyper_parameters 继承 text model、prompt 条件、REVE 边界设置与学习率；micro-batch 默认取源 bsz_train，梯度累积把有效优化 batch 补到 576；--text-devices 4 使用 DDP。checkpoint 写到 artifacts/<dataset>/glim/<encoder>/checkpoints，之后的推理优先使用这份 v3 checkpoint。
